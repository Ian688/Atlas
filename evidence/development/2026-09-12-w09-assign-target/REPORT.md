# W09：`unmodeled_assignment_target` 的归因（一次被自己的测量否掉的"修复"）

窗口：`2026-09-12/w09-assign-target`
结论：**DELIVERED（归因完成，无代码改动）**。查清了上一轮留下的 34 例；我提交的"修复"被自己的测量否定并已撤回。

## 1. 问题

上一轮全库对照发现：`unmodeled_assignment_target:=` 在 34 个函数上新出现，**34/34 都是循环函数**。
两个候选原因：
(a) 我发出的**循环变量赋值**目标建模失败；
(b) 循环体里本来就有这类赋值，只是以前整块未知、从未被 lower，现在才浮出来。

## 2. 先试 (a)，并用测量检验

`assignTarget()` 只有一种失败方式：符号查不到就返回 `{target:'unknown'}`。
所以我把 binder 改成**直接用 `register()` 返回的绑定 id**（绕开符号查找），重建 rxjs 并与上一轮逐函数对比：

| | 第 7 轮（改前） | 本轮（"修"后） |
|---|---|---|
| 带 `unmodeled_assignment_target` 的函数 | 317（循环函数 42） | **317（循环函数 42）** |
| CFG 块总数 | 47718 | **47718** |
| 返回值无结论 | 5627 | **5627** |
| flow 层调用点 | 11428 | **11428** |

**逐项完全相同**——说明符号查找本来就没失败过，**(a) 被排除**。
既然没有任何可测量的效果，我把这次改动**撤回了**：没有证据支持的"修复"不该留在树里，
哪怕它看起来更稳妥。

## 3. 再验 (b)：直接看源码

取「既是循环函数、又带该理由」的全部 42 个函数，把每个函数的源码切出来找元素访问赋值：

| 函数 | 命中 |
|---|---|
| `<anonymous@23562>` | `t[p] = s[p]`（`__assign` 的循环体） |
| `__assign` | `t[p] = s[p]` |
| `__rest` | `t[p] = s[p]`、`t[p[i]] = s[p[i]]` |
| `<anonymous@257479>` | `headers[key.toLowerCase()] = …`、`headers['x-requested-with'] = …` |

**结论：原因是 (b)。** `assignTarget()` 支持标识符与 `obj.field`，**不支持元素访问 `obj[key]`**——
这是一处**既有限制**，以前藏在"整块未知的循环"里，循环体被 lower 之后才如实报出来。
连 TypeScript 自己的 emit helper（`__assign` / `__rest`）都踩中它。

## 4. 这不是回退

42 个函数相对改前：CFG 块只增不减（全库 69 增 0 减），返回值 3 个从无结论变确定、0 个反向。
新增的理由是**以前看不见的真相**，不是新产生的问题——与第 8 轮那条 `capture_or_untracked_binding_read`
同一性质。**但"是真相"不等于"可以不管"**：它是真实的精度损失，且形状常见。

## 5. 下一轮该做的（需要两侧一起改）

支持元素访问赋值目标需要**同时改两侧**，这也是它值得单独一轮的原因：

- **worker**：`assignTarget` 为 `obj[key] = value` 产出目标形态（现有 IR 只有 `binding` / `property` 两种，
  需要新增一种，例如 `element`，带 object 与 key 两个被 lower 的子表达式）；
- **引擎**：认识这种目标，并给出**诚实**的语义——写入位置未知 ⇒ `may_write_heap = true`、
  且**不得**声称某个具体绑定被写入；若 key 可折叠成常量字符串，才可以退化为 `property`。
- 用例：`t[p] = s[p]`（未知 key）、`obj['x'] = 1`（常量 key，应收敛为 property）、`obj[k] = v` 后读 `obj`。
