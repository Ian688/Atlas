# Code Atlas 成熟产品能力合同：深度 Review、场景测试与画布 AI Coding

版本：1.3 · 2026-09-08。配套基线：开发设计 2.0、引擎算法规格 1.5、长期任务书 1.7、独立集成规格 1.3。本文是用户要求的成熟能力扩展及实施合同；所有新增接口、指标和场景均待实现 / 验收，不是当前 demo 的能力声明。

研究使用官方文档、公开协议、项目仓库和论文；成熟能力研究查阅日期为 2026-09-07；外部宿主能力补充查阅日期为 2026-09-08。本文没有实际安装或横向跑测这些第三方工具。商业价值判断、首批生态组合和新增数值目标属于产品建议，须用真实项目试验验证。

## 1. 成熟度判断与范围

现有设计已覆盖本地事实、语义算法、函数级执行、图形投影和受验证修改，但这些是必要基础。要交付可以承担深度 Coding / Review 的成熟 Atlas，还要明确：哪些真实生态可贯通、哪些缺陷可发现、哪些改造可完成、测试能否识别错误、LLM 怎样控制场景和视图、新代码如何进入同一个证据体系。

成熟的用户结果是：理解陌生系统 → 提出业务问题 → 绑定现有实现与契约 → 构造场景和反例 → 看见实际状态变化 → 修改多处实现 → 复验目标与旧行为 → 留下可复验的成果。每一段都能独立使用，也能连续工作；不能由一个成功计算器样例推定整个链路适用于大项目。

保留 Rust 核心、语言 worker、项目运行环境三层分工和主设计的 UI 形体。文件夹仍是平面分隔框、文件是玻璃柱、函数在柱内、实际 IO 驱动流动、结束留痕。新增能力不要求 LLM 成为解析器，也不要求先实现所有语言才能发布有明确范围的版本。

UP / CA 的原 23 个基础工作包保持有效，本文增加 MX-01–10 共 10 个成熟能力工作包，完整成熟目标合计 33 个工作包。基础 R3 是大项目资格；本文的 MR 成熟发布还要求所声明生态的场景、Review、改造与质量证据。它们可以穿插实施，不是先完成所有 UI 再考虑测试或语义。

独立能力补充见 [独立运行与外部 Agent 集成规格](/Users/yinsijie/CodeRepo/Modus/docs/code-atlas-standalone-integration-spec-2026-09-08.md)：同一核心服务 Modus 与外部 Agent，通用 CLI / MCP、冻结选区与请求邮箱、结构化状态读取和适用 HI 验收进入既有 MX；特定宿主 UI 和自有聊天按 profile 单独取得资格，不增加顶层工作包或用它们替代成熟能力。

双视图补充见 [3D 结构空间与 2D 关系工作台](/Users/yinsijie/CodeRepo/Modus/docs/code-atlas-dual-view-design-2026-09-08.md)：2D 为正式 Review / 测试 / Coding 入口，按问题生成本地关系投影；与 3D 共用选区、标注、事实和运行留痕。DV 纳入现有 CA / MX 与质量证据，不能仅以几何压平或降级图交付。

## 2. 成熟版本必须提供的具体能力

| 能力 | 用户能做什么 | 最低完成证据 |
|---|---|---|
| 真实架构与导航 | 查定义 / 实现 / 引用、入口、配置消费者、生成源和跨包依赖 | 对应编译 / 构建变体；同名、别名、重载和未知项正确 |
| 业务到代码映射 | 从“领红包 / 下单”找到页面、事件、路由、服务、存储与测试 | 每个映射有源码 / schema / 注册 / 运行依据，歧义可见 |
| 深度行为 Review | 追值来源、校验路径、状态写入、异常、权限与资源生命周期 | 具体条件、代码路径、反例或规则证据；不只给复杂度分数 |
| 变更 Review | 查看补丁改变了哪些接口、行为、资源和消费者 | 源码 diff、关系 / 契约 diff、受影响场景、已有 / 新增问题 |
| 局部到业务场景测试 | 测单函数、函数组、组件、接口、数据库和完整用户旅程 | 原始输入、上下文、真实 / 替身边界、断言、清理和回执 |
| 稳健性测试 | 找边界输入、操作序列、并发竞争、取消、重试和重复消息问题 | 可重放的反例、种子 / 时钟 / 调度条件、状态与 IO 证据 |
| 测试有效性分析 | 判断哪些代码有测试但没有有效断言、哪些修改易漏检 | 按目标统计覆盖与断言；定向变异 / 故障注入揭示薄弱点 |
| 故障定位 | 从失败结果回溯相关输入、分支、调用实例与状态版本 | 有序证据与未知边界；定位候选可继续验证 |
| 性能 Review | 分辨计算慢、IO 等待、N+1、锁等待、事件循环阻塞和泄漏 | 可比负载下的测量、资源与调用定位、探针开销 |
| 多文件 Coding | 改接口、迁移类型、提取模块、调整状态机、增加完整业务功能 | 相关实现 / 接入 / schema / 迁移 / 测试同步变化且验证 |
| 自然语言场景编排 | 用业务叙述创建可执行场景、变体与讲解路线 | 可校验 ScenarioPlan；LLM 操作经过工具服务，实际事件驱动画面 |
| 画布提出并开发功能 | 在已有模块 / 端口旁描述新能力，查看设计占位到真实代码 | 意图、拟新增对象、源码 patch、解析、测试和落地可追踪 |
| 本地工程操作 | 模型关闭时导入、查询、重构受支持模式、运行已有场景、查报告 | 产品 provider 调用为 0；无隐式云索引或全仓上传 |
| 大项目可靠性 | 长时间索引、增量更新、取消恢复、跨版本比较和同时 Review | 主设计 L 档资格；没有错版事实、静默遗漏或混合回执 |
| 团队可交接 | 共享准确版本的发现、场景、约束与验证包，在 CI 复验 | 本地导出 / 导入、CLI、编辑器定位；远程发布按现有授权 |

每项能力至少有一条真实用户任务和一组失败反例。UI 按钮、协议定义、接入一个库、生成一份报告均不能单独构成“该能力已完成”。

## 3. 支持范围：按生态组合取得资格

“支持 Python / TypeScript”不足以帮助用户判断能做什么。CapabilityProfile 应至少包含语言 / 版本、构建系统与变体、框架、语义特性、运行入口、IO、重构操作、测试类型、OS / 目标环境、资源上限、验收语料和已知缺项。解析、深分析、执行、改造四个维度分别显示。

建议首个成熟商业版本把 JS/TS 与 Python 做到完整日常开发深度；新增语言按相同合同取得资格，不能把大量 L1 语言宣传为同等深度支持。以下为候选首批组合，MX-01 用真实样本固定具体版本与分发方式，不能仅拿计算器替代：

| 生态组合 | 成熟首批要求 | 后续扩展方式 |
|---|---|---|
| TS Web 前端 | React 与 Vue 分别具备组件 / 事件 / 状态 / 请求的真实适配；一种实际构建链及 Playwright 接入 | SSR / 框架服务端组件、其他构建链逐个验证 |
| Node 服务与 Electron | ESM/CJS、多包、异步、一种 Web 框架；Electron IPC / preload / 文件 / 剪贴板 | 增加框架、队列与 native 边界模型 |
| Python 服务 | FastAPI、类型 / decorator / async、SQLAlchemy、pytest fixture 与目标解释器绑定 | Flask / Django / worker 框架取得同级资格 |
| 数据与协议 | OpenAPI / JSON Schema、HTTP、SQL / 事务、一个实际队列后端、生成客户端映射 | protobuf / gRPC / GraphQL、更多数据库 / broker |
| Go / Rust | 按各自工具链实现导航、配置变体、入口执行与语义规则；分别公布阶段 | 从 L1/L2 升级到完整 Review / 测试 / 改造，不按 Rust 引擎语言推定 Rust 项目已支持 |
| Java / C# / C/C++ | 对应编译语义、构建 / 平台、框架和测试适配是独立资格工程 | 首个成熟版本不虚报全覆盖；有目标客户后按完整生态包扩展 |

首批 JS/TS 特性语料需包含：作用域 / 闭包、类 / 私有成员、别名、ESM/CJS、类型与运行实现区别、Promise / async、generator、finally、回调注册、动态属性候选、框架 DI 与多实例。Python 需包含对应作用域、导入、类、decorator / descriptor、闭包、异常、async / generator 与 monkey patch 未知边界。普通受支持代码大量回退 unknown 或 unavailable，属于质量不合格。

一个项目有不支持组件时，显示“哪些业务链断在什么边界、需要什么适配”，不能只有文件级支持百分比。关键支付回调未支持，即使 99% 文件能解析，也不能宣称该支付场景已完整验证。

CodeQL 显式列出语言和框架模型；SCIP 提供语义导航交换，不能单独解决数据流与框架生命周期。它们说明支持范围需要以模型和工具链细分。[CodeQL 支持范围](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)、[SCIP](https://github.com/scip-code/scip)

## 4. 从代码结构到业务对象的本地连接

增加版本化 DomainBinding，将业务术语连接到 UI 元素 / 事件、函数、Endpoint、消息、数据 schema、资源及已有测试。来源有四类：本地解析器 / 框架规则、项目明确配置或用户标注、真实运行绑定、LLM 提出的语义候选。LLM 候选不能覆盖事实；业务名称允许一对多和多对一。

“红包”可能是 coupon、voucher、promotion，也可能多个模块共同实现；不能仅靠英文命名匹配。模型可借助本地词法搜索、符号摘要、注释和相关源码调查；确认依据必须回到原始锚点。动态 UI 到 handler、HTTP client 到服务、数据库列到模型属性分别需要适配器 / source map / schema 或运行关联，禁止凭同名拼接。

BoundOperation 描述业务可用动作：动作 ID、参数 / 输出类型、实际入口、前置条件、状态效果、fixture、真实 / 替身能力、断言支持、相关代码与版本。一个动作可由多个步骤实现；一个底层函数可参与多个业务动作。没有找到实现时返回 missing_operation，可进入功能设计流程，不能为既有场景虚构一个可运行 API。

此层由本地索引支撑，但自然语言歧义与业务取舍允许由 LLM 处理。用户已明确的业务约束直接作为需求；项目材料冲突且影响预期时明确显示冲突，只有无法从现有信息决定的关键取舍才询问，不能每条操作都要求确认。

## 5. LLM 操作 Atlas：职责与工具合同

在 Modus 中，Modus Agent 负责对话、模型预算、任务推进和授权协调；LLM 提出业务解释、场景或补丁；Atlas 服务负责实体解析、计划校验、执行、证据与画布投影，接入现有 Agent Runtime。独立模式由 Host Adapter 对接外部 Agent 或自有聊天客户端，通用服务不依赖 Modus 私有会话；每种模式沿用其实际授权、模型预算和执行边界，不另外建立绕过这些边界的调用通道。

模型需要可查询的能力摘要：当前快照、已支持操作 / schema、入口候选、目标可测性、环境、未知项和后续查询入口。上下文按当前步骤编译；不把全仓图、所有 trace 值或所有工具描述一次塞入模型。

| 服务操作扩展 | 输入 / 返回 | 约束 |
|---|---|---|
| `code_atlas_capabilities` | 项目 / 当前版本 → profile、可用动作、schema 与缺项 | 只读；返回能力版本 |
| `code_atlas_domain_resolve` | 业务词 / 目标 / 选区 → 带证据的操作候选 | 未匹配不虚构，不通过加载执行项目找答案 |
| `code_atlas_scenario_validate` | ScenarioPlan → 类型 / 绑定 / 前提 / 策略 / 预算诊断 | 只校验，不启动真实动作 |
| `code_atlas_scenario_prepare` | 已校验计划 → ExecutionContextPlan / 环境准备需求 | 延续现有接口，实际 setup 属于 Runner |
| `code_atlas_scenario_run/cancel` | plan + 环境 / 输入引用 → run / 回执 | 幂等 key、取消与状态查询；超时不自动重复副作用 |
| `code_atlas_view_command` | 实体 / run / 证据引用 → 聚焦、展开、时间游标或计划预演 | 不能写事实、伪造 run 事件、将目标强制标为通过 |
| `code_atlas_design_intent_put` | 描述 / 选区 / 约束 → DesignIntent 与拟新增图版本 | 仅修改设计材料，未生成源码前不增加实际函数计数 |
| `code_atlas_change_prepare/execute` | DesignIntent / ChangeIntent → patch、验证、应用结果 | 复用既有变更与工具授权，不能绕过基线检查 |

Agent 侧 `atlas.scenario`、`atlas.change` 包装这些动作，新增 `atlas.capabilities / domain / view` 等有界入口；共享同一实体和授权服务，不维护第二套同名事实库。工具参数与输出使用 schema、枚举和引用，代码 / 任意命令只通过已有受控开发工具。MCP 的结构化输出和资源引用可作为协议参考；Atlas 不要求必须依赖 MCP 才能本地运行。[MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

ViewCommand 至少含 owner / project、snapshot 或 run、graph_layer、entity / evidence refs、action、request_id、expected_revision。模型可以请求 focus / reveal / fit / seek / compare / preview_plan；不提供 force_activate 或直接设置 visited / passed 的能力。未知实体、错误 run、过期快照返回可恢复诊断；用户当前视图可固定，避免讲解每一步都抢镜头。收到 view 回执才说“已展开”。

事实、执行与展示使用同一来源链，但有独立状态：已选中、计划经过、实际执行、历史经过、拟新增、已解析、已验证不能仅靠同一种颜色表达。图例同时使用线型 / 标签，照顾色觉与低动效设置。

## 6. 自然语言场景：外卖 APP 的完整执行通路

### 6.1 用户请求到可执行方案

对于“查红包—领红包—浏览商品—下单—使用红包—支付”，LLM 先明确用户希望演示既有实现、测试其正确性，还是要求新增缺失功能；结合当前请求与项目上下文判定，不机械地追问三遍。

执行通路为：自然语言目标 → ScenarioIntent → 业务动作与源码绑定 → ScenarioPlan / 断言草案 → 本地校验与上下文准备 → Runner 执行 → 事件和状态差分 → 投影 / 报告 → LLM 按证据讲解。预演可以先于执行，但有计划标签；执行动画只由当前 run 事件驱动。

ScenarioIntent 保存用户目标、角色、选区、输入域、期望结果、约束、业务假设与来源。ScenarioPlan 保存步骤 / 分支 / 有界循环、输入绑定、前置 / 后置条件、动作模式、故障注入、完成条件、断言、环境与成本上限。具体语法在 MX-03 实现；不得仅存一段 Markdown 再让执行器猜着跑。

| 步骤 | 必要状态与输入 | 主要观测 / 断言 |
|---|---|---|
| 查红包 | 测试用户、身份、租户、活动与时钟 | 列表归属 / 有效期；不泄漏其他用户红包 |
| 领红包 | 活动资格、领取上限、幂等键 | 领取记录、数量限制；重复请求不会重复发放 |
| 浏览商品 | 商家、库存、价格版本 | 页面 / API 与当前价格数据一致，选中商品可追溯 |
| 下单 / 用红包 | 购物车、地址、门槛、优惠叠加规则 | 服务端重算金额、红包归属与状态、订单 / 库存事务 |
| 支付 | 订单状态、支付适配器、请求幂等键 | 请求金额、支付状态、回调验证与订单最终状态 |
| 完成 / 失败恢复 | 异步回调、超时、重复 / 乱序消息 | 不重复扣用红包；失败按已定义契约释放 / 保留占用 |

上表是用来设计测试的业务问题，不是宣称用户项目恰好采用这些规则。具体“先下单再锁券还是先锁券”等顺序从源码 / 契约绑定；退款是否退券、门槛是否含配送费等必须引用项目需求，不能被通用模板强行决定。

### 6.2 场景 IR 的最低形态

```text
ScenarioPlan:
  identity: project, snapshot, plan_revision, model_and_tool_versions
  goal_refs, assumptions, unresolved_bindings
  actors: [test_user, merchant_fixture, callback_sender]
  environment_ref, fixture_refs, clock_seed, random_seed
  steps: [Step(id, operation_ref, depends_on, input_bindings,
               preconditions, driver, effect_mode, timeout, outputs)]
  branches: [condition_ref, alternatives]
  loops: [condition_ref, max_iterations, max_wall_time]
  expectations: [AssertionSpec with requirement provenance]
  fault_injections, observation_spec, limits, cleanup_plan
```

值绑定使用类型化 step_output / fixture / literal 引用，例如 order ID 取本次 create-order 输出，不能让 LLM 重新填写一个猜测值。并行 fork / join、等待回调、失败中止 / 恢复是显式结构；默认顺序计划不自动将所有步骤并发。

编译器先检查 ID、版本、入口、依赖是否存在和类型是否匹配，再检查变量定义支配使用、前置条件材料、循环 / 等待上限、环境与效果能力、断言所需 probe。静态图可达不等于业务状态可达；模型生成的 guard 不能直接作为源码事实。无法验证的前提保留为运行检查或未决项，不能静默删去。

关键不变量可用受限状态 / 数值 / 集合规则表示：同一红包最多成功消费一次；已支付订单的应付金额与支付请求一致；失败 / 取消后的资源状态符合契约。金融金额使用项目规定的精度与舍入约定，不能由展示浮点数推导正确性。规则转换与代码绑定各有版本，测试目标是实现是否满足规则。

### 6.3 场景测试与数据造影

本地 Runner 可采用实际 UI 操作、HTTP 驱动、消息驱动或受支持函数入口。直接调用服务函数能验证该层行为，但不能由此声称点击按钮到页面反馈已经通过；用户旅程资格需要实际 UI / API / 状态链的证据。

准备专用测试用户、商品、订单库与受控依赖。支付使用明确的替身或支付机构测试环境，报告逐边标记模式；替身支付可以验证订单处理，但不能冒充生产支付成功。对声明真实数据库 / 队列的场景，使用实际受控服务验证事务、重试、提交和消息确认，而不是只给内存对象赋值。

运行事件携带 scenario_run、step、actor、invocation、span / message correlation、state version、sequence 和资源身份。UI 关联“领红包”步骤与实际函数层，显示券 ID / 金额的本地摘要、状态变化、分支、等待和异常。跨进程因果优先使用传递标识与 span link；时间先后和金额相同都不足以证明数据派生。[OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/)

按用户选择提供正常路径、红包过期、金额刚好达到门槛、重复领取、并发用同一张券、支付超时、重复 / 乱序回调、库存不足等变体。每个变体独立回执；可并排比较“正常 / 异常”“修改前 / 修改后”。失败后保留已经过的管道，其余灰色静默，不补播未执行的成功步骤。

暂停的含义分开：暂停回放只停展示，业务可能已经结束；暂停业务需要驱动 / 调试器在受支持边界挂起。改变输入或注入故障创建新的实验 run，不能篡改旧记录并声称是原来的执行。

### 6.4 LLM 讲解与场景自修复

模型可以先说计划、运行中解释已到达步骤、运行后解释失败与差异。上下文按步骤完成 / 异常 / 用户停留等事件批量生成，包含精简事实和可按需读取的源码 / 报告引用，不为每帧动画调用模型。每段讲解绑定 plan / run / snapshot / evidence，迟到结果不替换新运行说明。

执行失败时区分：计划绑错入口、fixture / 环境缺项、驱动定位失效、业务断言失败、采集缺口。模型可以修改前几类材料并创建新版本重试；不能删除失败断言、扩大等待到无上限、用 fake 替换 real 而不改声明，或修改产品预期来让测试变绿。业务修复进入 ChangeIntent。

GraphWalker 说明动作、状态验证和路径生成可以形式化；Playwright Test Agents 已提供 planner / generator / healer 的组织方式。Atlas 应吸收其计划与执行分工，并将输入绑定、测试预期和真实 IO 证据做得更严格。[GraphWalker](https://graphwalker.github.io/)、[Playwright Test Agents](https://playwright.dev/docs/test-agents)

## 7. 在画布上描述功能并持续生成代码

### 7.1 设计意图是可保存、可定位的对象

用户可以在文件夹框、文件柱、函数层、端口或跨模块选区上添加功能描述。例如在“红包计算”旁写：“新增自动选择最优惠红包；支付失败按现有契约恢复可用状态”。空白处也可创建拟新增模块，注明所属包 / 文件和接入点。

DesignIntent 保存描述、所在选区、输入输出、必须保持的行为、拟新增对象与关系、业务假设、验收场景、目标分支 / 工作区和基线。用户拖一根拟新增连线可能表示“希望调用”“希望传递某字段”或“依赖此服务”；关系种类必须明确，不能把任意几何连线直接编译为一段正确代码。

### 7.2 三类图与源码状态转换

| 图 / 状态 | 数据来源 | 画布含义 |
|---|---|---|
| IntentGraph，拟议中 | 用户描述与模型方案 | 虚线占位柱 / 函数层 / 管道；标“拟新增”，不计入已有代码对象 |
| CodeGraph，当前或候选源码 | 指定源码快照的本地解析 | 已存在对象与确定 / 候选关系；候选工作区与原工作区分别标识 |
| RunOverlay，已观测 | 对应构建和快照的真实运行 | 本次实际激活、数据与断言；未执行不显示已验证血流 |

```text
intent_draft → design_bound → patch_streaming → candidate_snapshot
            → parsed | parse_error → validation_pending
            → verified | failed | inconclusive → applied → reindexed
任一依赖版本变化 → stale / conflict；取消保留可恢复草稿和已有证据
```

占位对象使用 `intent:` 身份空间，与 parser 的实体 ID 分开。ProposalBinding 记录拟议对象到实际 entity 的映射，可一对多、部分完成或歧义；只有本地解析确认对应源码存在才能建立 materialized 关系。LLM 声称“已新增函数”不能直接把占位变为正式函数。

### 7.3 实时生成、解析与展示

模型可以流式提供解释和补丁，但临时 token 不直接写入原工作区。编辑协调器在独立候选工作区或版本化编辑 overlay 聚合完整文件 / 变更块；形成有 hash 的候选快照后增量解析。语法未完成时保留编辑草稿 / 错误区与上一个可读图，不伪造调用关系，也不抖动删除整个文件柱。

本地文件 watcher 同时接收用户、Agent、codemod 和编辑器更改。变更按版本去重、合并与失效，发送 GraphDelta；renderer 保持目录 / 文件位置与选择锚点，对新增 / 删除 / 改名进行渐进显示。公共契约或依赖变化使相关解释、测试计划和结果过期；旧图可留作对照，不能混入新的 current。

每个新功能展示四个独立进度：源码已生成、解析 / 类型 / 构建情况、接入场景情况、目标测试与回归情况。创建一个没有调用者的函数可以是有效库 API，但“APP 新功能已完成”必须验证其真实接入点；不能把孤立函数的存在当作用户入口可用。

### 7.4 多文件开发与审查

“自动选红包”可能涉及策略函数、结算服务、API schema、页面选择反馈、存储模型和测试。影响计划应逐项说明需变更 / 需验证的位置，读范围与写范围分离；当前授权覆盖的必要修改持续推进，超出授权时先准备具体方案与 diff。

AI 与本地 codemod 配合：确定的符号重命名、导入修复、已支持迁移优先用语义操作；业务决策与复杂实现由模型提出。所有来源的补丁均进入同一验证链。OpenRewrite 的类型信息 / 格式保持与 LibCST 的源码保持思路可用于减少无关差异，但不能据此推定任何重构都保持行为。[OpenRewrite LST](https://docs.openrewrite.org/concepts-and-explanations/lossless-semantic-trees)、[LibCST](https://libcst.readthedocs.io/en/latest/)

删除 / 移动 / 合并器官同样生成源码变更和接入迁移；图操作不是直接改事实表。冲突时保留方案、补丁与已完成测试，重新绑定后再验证，不能覆盖另一个 Agent 的工作。

## 8. 测试能力的深度：从输入到状态序列

成熟测试至少覆盖以下层次，按适用 profile 验收，不能只接一个单测命令就算完成：

| 层次 | Atlas 的实际操作 | 重点失败样例 |
|---|---|---|
| 单函数 / 方法 / 闭包 | AL-16 准备上下文、注入原始输入、捕获返回 / 异常 / 状态 | 非法类型、未初始化实例、捕获变量错误、目标未触达 |
| 多函数 / 组件 | 实际依赖调用和控制分支，按调用实例检查值 | 参数传错、状态泄漏、回调注册未执行、await 缺失 |
| API / 消费者契约 | 从 schema / 已有契约生成输入并执行 provider 验证 | 字段删除、nullable 改动、状态码变化、消费者不兼容 |
| 数据与集成 | 临时真实数据库 / 队列、事务、提交 / 回滚和消息确认 | 写一半失败、重复消息、缓存与数据库不一致 |
| 用户旅程 | 真 UI 或明确 API 层的业务步骤与反馈 | 页面提示成功但后端失败、权限错误、缺少交互接入 |
| 性质 / 变形测试 | 指定输入域、不变量和转换关系，本地生成与收缩 | 金额不守恒、排序结果与选择策略矛盾、序列化无法回读 |
| 状态机测试 | 基于明确模型生成有界操作序列 | 重复领取、取消后支付、退款后重复回调、非法状态跳转 |
| 并发 / 故障测试 | 控制 actor、屏障、超时、乱序、重试与故障边界 | 同券双花、库存超卖、取消未清理、死锁 / 等待泄漏 |
| 变异与测试审查 | 定向改变校验 / 运算 / 状态更新，检查既有断言能否发现 | 删除金额校验后仍全绿、只断言没有抛异常 |
| 性能 / 长时间测试 | 固定负载、资源与采集策略，比较多次运行 | N+1、吞吐回退、队列积压、句柄增长、事件循环阻塞 |

复用既有测试框架和 fixture，而不是强迫项目迁移到 Atlas 专有测试语言。生成的测试应可导出并通过项目测试命令复验。动态测试 discovery 属于执行，不混入文件扫描；测试适配器声明其 setup、过滤、reporter、取消和环境需求。

状态机算法以明确动作 / 状态模型为输入，采用预算内的 BFS / 随机 / 覆盖引导探索，记录访问抽象状态、边覆盖、种子和停止原因；大量序列用去重和部分等价策略控制，但等价依据要验证。静态源码不能自动提供全部业务正确规则。Hypothesis 可生成和收缩操作序列；Schemathesis 可从 API schema 生成性质测试；Pact 将消费者期望与实际 provider 响应分别验证。这些能力可以由本地执行器组合。[Hypothesis stateful](https://hypothesis.readthedocs.io/en/latest/stateful.html)、[Schemathesis](https://schemathesis.readthedocs.io/en/stable/)、[Pact](https://docs.pact.io/getting_started/how_pact_works)

失败样例要能保存并重试；收缩输入或动作序列时保持必要前置状态和原失败断言，不能删除关键 setup 后得到另一种错误却说已经找到最小反例。并发样例记录调度 / 屏障和外部条件；无法确定性重现时报告复现频次，不许诺任意分布式程序的精确重放。

测试有效性单独计量：代码是否被执行、断言是否覆盖关键 claim、故意引入相关错误能否被发现。变异分数不是程序正确性的证明，等价变异、超时、无覆盖和无效变异分别记录；不能删除难杀的变异来装饰分数，也不强求通用 100%。[Stryker equivalent mutants](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/)

## 9. 深度 Review 必须给出可行动的问题

除了源码导航，至少建设以下发现类别的本地规则 / 分析适配：输入校验与空值、异常处理与取消、资源释放、权限 / 租户隔离、敏感值传播、状态机与幂等、事务一致性、API / schema 兼容、配置 / 环境差异、依赖方向 / 循环、异步等待与重试、可证实的性能反模式。业务依赖较强的规则由项目约束补充，LLM 可以提出假设，不能把通用描述当成已发现 bug。

例如“红包可能有风险”没有行动价值。合格结果应说明：哪个入口、哪类身份 / 输入、哪个分支缺少校验、可能影响哪个写入、已有何种静态或实测证据、如何复现、建议补哪项约束、目前还有哪些未确定边界。

Finding 最低字段：rule / producer / version、snapshot、源位置与相关位置、触发条件、证据类别、路径 / 反例引用、影响 claim、严重性理由、未知项、复现方案、相关测试和修复后核验方式。LLM 推断、静态可能问题、可重现失败和约束验证结果分别表达；一个简单数字 confidence 不能替代证据。

在变更 Review 中区分原有问题、新增问题、修复问题与因范围变化未重验的问题；按根因合并重复报警，保留关联位置。抑制 / 接受风险记录原因、作用范围、版本和到期 / 失效条件，不能永久静默掩盖后续变更。

安全与行为分析的可用开源组件、商业引擎和自有 Rust 算法要明确分工。例如 Semgrep 官方区分 CE 的函数内分析与 Semgrep Code 的跨函数 / 跨文件能力；接入 CE 并不自动获得后者。Atlas 需要实现或合法接入自己宣称的分析深度，不能用工具名代替覆盖声明。[Semgrep 跨文件分析](https://docs.semgrep.dev/semgrep-code/semgrep-pro-engine-intro)

## 10. 深度 Coding 的完成标准

成熟 Coding 支持三类路径：确定语义下的本地重构、模型生成复杂业务补丁、用户手工编辑；都通过同一版本、影响和验证链。LLM 不可用时前两者中的本地部分、源码编辑、测试和报告仍可使用。

必须可完成的任务包括：跨文件重命名 / 移动、提取或合并模块、接口参数 / 返回类型迁移、共享 DTO / schema 变更、配置 / 数据迁移、异步流程调整、依赖升级、性能问题修复，以及页面—接口—业务—存储—测试的新增功能接入。每个操作按 profile 取得资格，不承诺任意复杂重构自动保持行为。

ChangePlan 除源码目标外列出：公共接口、调用者、序列化 / 持久化兼容、生成源、运行环境、部署配置材料、相关断言与测试选择理由。数据库迁移在临时数据上验证前后兼容与恢复；生产迁移不是本地编辑自动附带的动作。

修复任务要求目标反例在原版失败、候选版通过，相关旧行为保持；若需求本来改变行为，明确更新契约依据和被替代预期。新增功能使用独立需求断言和真实接入测试。测试代码与生产代码同时被模型修改时，独立验证器检查断言是否被弱化，保留不可由该模型修改的验收材料。

多步骤改造保存任务依赖、已完成补丁、剩余验证与基线。模型中断、工具失败、上下文耗尽后从已验证阶段继续；另一 Agent 修改相关内容时做冲突处理、重绑定与重测，不清空整个项目。代码生成速度、补丁行数和模型自报完成率不能作为正确性指标。

SWE-Bench Pro 把复杂软件任务扩展到长过程与多文件改动；SWE-Bench+ 的研究指出，弱测试可能让有问题的补丁得到通过结果。这支持 Atlas 采用真实任务、独立预期和多层验证，不照搬某个排行榜得分作为产品质量。[SWE-Bench Pro](https://arxiv.org/abs/2509.16941)、[SWE-Bench+](https://arxiv.org/abs/2410.06992)

## 11. 调试、性能与长期工程可靠性

同一选区可切换结构、数据来源、时序、状态、变更和性能投影；底层实体一致，各视图回答不同问题。用户应能从某个错误输出倒查到相关调用实例、输入、分支、状态写入和事件缺口，并在已有源码与报告中定位。

运行分析提供时间窗、span / 调用实例、错误过滤、对象 / 资源写入记录和两次场景比较。字段级来源仅在有对应静态规则 / probe 时提供；OTel span 不能直接冒充每个函数和变量的观测。UI trace 截图、DOM snapshot、网络与源码可作关联材料，但 Playwright 测试步骤的源码位置不是 APP handler 的源码映射，需要另行桥接。[Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer)

区分三种回放：只读事件回放、固定输入的新运行、特定后端提供的确定性录制 / 重放。rr 展示了第三种路径，但有平台、并行与系统调用边界；不能把它当所有浏览器、macOS 与分布式系统的通用保证。[rr](https://rr-project.org/)

性能证据至少分 CPU、等待、IO 次数与大小、数据库请求、锁 / 队列、内存和资源寿命；比较时固定工作量与环境并报告 probe 成本。图中的管道粗细若代表吞吐或延迟，图例必须有单位、窗口和聚合口径，不用随机动画速度表达性能。Perfetto 的可查询 trace 处理是可借鉴的材料组织方式。[Perfetto Trace Processor](https://perfetto.dev/docs/analysis/trace-processor)

延续主设计第 22 节的 L 档规模、局部查询 p95、内存、取消和增量门槛；新增规划、LLM 流式输出和运行采集同时发生时也要验证。默认不开全仓全部变量采集；按场景 / 选区渐进启用，给出可见预算和数据缺口。缓存 / schema 升级、worker 崩溃、磁盘满、依赖服务退出和订阅重连都须有恢复结果。

## 12. 质量合同：既限制错误，也限制大量“不支持”

CapabilityReceipt 同时记录：宣称范围、实际输入分布、已完成任务、失败 / 未支持 / 超时、正确性与资源结果、源码 / 环境 / 模型版本和证据。任务成功率的分母包含该范围内的 setup 失败与能力缺项；另报原因，不能只统计容易运行的样本。

以下是建议冻结的成熟发布目标，属于 Atlas 的产品门槛草案，不是行业公认数值或已测成绩。MX-10 在实施前固定任务集与计算方式；调整要有数据和范围变化记录，不得跑完再降低门槛。

| 维度 | 候选门槛与评价方式 |
|---|---|
| 事实与版本 | 全部规定反例中不允许错版绑定、伪造执行 / 通过、静默丢失、不当跨项目读写；任一出现阻止对应资格 |
| 语义精度 | 沿用主设计 resolved precision ≥99%、支持集 recall ≥95%；分语言 / 框架 / 关系抽样，报告置信区间与未知比例 |
| 普通任务覆盖 | 声明首批生态的资格语料中，至少 95% 的适用基础动作能完成查询或准备运行；目标缺项不得用全局文件支持率遮盖 |
| Review 有效性 | 对独立标注的高优先级发现 precision 目标 ≥90%，对指定缺陷类别的种植 / 历史真实 bug recall 目标 ≥90%；两种语料分别报 |
| 场景生成 | 明确契约和已支持驱动下，成功绑定并执行预期业务步骤目标 ≥90%；生成 plan 合法不等于业务测试成功 |
| Coding 正确完成 | 冻结的有界任务集在固定总模型 / 时间预算内独立验收成功目标 ≥80%；修复、增功能、迁移分别报，不能只用单函数题 |
| 测试判别能力 | 为每个关键业务 claim 注入至少一个相关错误，规定样例必须检出；定向有效变异检测率目标 ≥90%，等价 / 无效 / 超时单列 |
| 交互与资源 | 不降低主设计第 22 节门槛；模型思考不阻塞查看源码 / 留痕；候选编辑和长 trace 下测 p95、RSS 与恢复 |
| 本地边界 | 关闭模型后全链导入、profile、已存场景执行、断言报告与回放可用；真实 provider 调度计数为 0 |

基准至少覆盖 8 个固定版本的真实项目 / 独立业务样本和 80 个任务，含团队获授权的未公开任务或未公开变体；首批重点生态各有多个项目，避免单一框架样例代表全覆盖。公开仓库任务与未公开任务分别报，不宣称某种设置可以完全消除训练污染。

MT-01–24 是场景族目录，不是仅需运行 24 次；为每类绑定具体 fixture、项目、模型条件、预期与反例。另用主设计算法 golden 和 ET 验证底层正确性，不能由高层任务成功掩盖错误关系。统计逐项保留样本量与区间，测试“0 次事故”不推导未来绝无事故。

## 16. “叫好又叫卖”的验证方式与交付检查

商业定位属于待验证判断。优先验证三类重复发生的付费需求：接手复杂项目并找到真实问题；审查跨模块改动并降低遗漏；新增业务功能后取得可信的测试和交接材料。玻璃架构负责让这些任务更容易理解与操作；模型 token 下降是成本指标之一，还要统计用户时间、返工和错误率。

真实用户试验应比较相同项目 / 同等模型预算下的常用 IDE / 测试工具流程与 Atlas；任务包含成功路径和困难反例，记录定位 / Review 时间、正确完成率、遗漏、误报处理时间、返工、持续使用与愿付费证据。先做可用性小样本，再按观察到的效应设计正式对照；不能从少量好评宣称普遍效率提升。

建议在 MR 之前完成一个外卖类多层参考应用和多个无关真实项目。前者验证业务全链和异常状态，后者验证通用性；改函数名、文件布局、框架版本、DI 实现和测试工具后仍可工作，才能避免只能展示定制 demo。测试依赖应可本地创建，场景与报告可导出复验。

本轮交付是能力合同与研究整理，不包含生产实现。文档校验覆盖章节、MX / MT 编号、交叉版本、本地引用、围栏和格式；其结果只证明文档组织自洽，不证明场景编译、模型工具协作、画布开发或成熟质量门已通过。正式实现按第 14 节进入长期任务书，并保留原基础工作包的证据。

## 17. 首轮实现审查后的证据与场景约束

上述研究交付记录为历史说明。本次 1.3 依据 [实际源码审查](code-atlas-implementation-review-2026-09-08.md) 补强成熟门；当前仍未达到 MR。先完成本地分析/运行反例整改，再扩大 LLM 场景协作范围。

自然语言场景编译必须保存三份不同材料：用户要求与业务假设、经本地验证的计划、实际执行观察。比如“领红包→下单→使用红包→支付”可预先显示计划路线，但余额改变、红包核销、支付成功需要对应真实效果与断言；模型或本地模拟推导不能充当数据库 commit 的观察证据。

ScenarioPlan 固定项目/源码/分析版本、入口/角色、前置数据与真实/替身依赖、步骤的依赖关系、输入生成策略、断言 oracle、资源与效果边界。prepare 明确可执行入口和缺项；run 使用冻结材料并持有幂等身份。用户可比较多个方案，不应因为切换 2D/3D 或 Agent 重试而再次支付/写库。

结果至少分开 execution、assertion、trace transport、instrumentation coverage、effect observation、cleanup。无 trace 丢包不等于所有函数被采集；run completed 不等于异步业务完成；mock 调用记录不等于真实 readback。函数值/类型、异常、时序、数据库事务、文件/剪贴板效果各自用对应 oracle。

AI Coding 的依赖材料不得消费有已知漏项却标为完整的摘要。ContextPack 携带 query scope、source windows、coverage、未知与截断；不足时继续本地检索或说明缺项，不能用 LLM 补造关系。IntentGraph 占位与实际 CodeGraph 分开；变更应用之前验证基线版本，应用后重新解析受影响范围与负查询依赖，再做场景/回归验证。

新增强制反例归入既有 MT：重复场景提交只执行一次；预期成功但未发生真实效果；async 未 settled；采集目标缺失；源码在准备后变化；候选代码影响未返回的第三/第四层函数；同一选区切视图不重跑；父子并发 span 不误画为单一顺序线路。

完整运行记录保留本地，LLM 仅取得必要摘要和源码。线上遥测、真实数据访问和自动恢复仍按生产诊断提案另行取得能力/权限资格；MR 的离线/测试环境结果不自动变成生产授权。
