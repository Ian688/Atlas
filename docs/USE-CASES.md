# Atlas 使用场景：人做什么、Atlas 做什么、LLM 做什么

这份文档回答一个问题：**Atlas 存在的意义是什么**。它不是功能清单，是把"决定"拆到三个承担者身上的分工表。每个场景都注明**今天能不能做**，因为一个做不到的场景比没有场景更危险。

## 前提：Atlas 独占的三件事

1. **不可伪造的"不知道"。** 带覆盖数字、带原因、带预算边界。LLM 会顺口补一个听起来对的答案，Atlas 必须说"这里我没有事实"。
2. **同一问题在同一快照上给同一答案，并可回到源码锚点。** 可复现、可审计、可写进 CI。LLM 做不到。
3. **真的在隔离副本里跑起来。** 把"我认为"变成"我观察到"，并且区分 `timeout` / `cancelled` / `refused`——它们不是同一件事。

## LLM 独占的三件事（Atlas 不许抢）

1. **意图与业务语义**：为什么这样写、这段代码想干什么。
2. **综合与联想**：把结构、历史、issue、规范、口头知识连起来。
3. **生成**：补丁、测试、解释文案。**但证据由 Atlas 给，决定由人做。**

**人独占**：判断与承担后果。

---

## 1. 接手陌生仓库，要改一个函数

- **人**：明天要改 `redeemCoupon`，不知道碰它会炸哪里。
- **Atlas**：谁调用它（已解析的有几个）、它调用谁、值从哪来、哪里未知、能不能独立跑、依赖包络多大。
- **LLM**：解释这个函数在业务上干什么、建议怎么改。
- **Atlas 的作用**：把**影响面的确定边界**画出来，并明说哪些部分它没有事实。
- **今天**：能做（reach/flow/profile），但**画布点不动**——第一页 0 个函数，邻居盒子标"未载入"。

## 2. 线上事故：这个函数的行为是否变了

- **人**：怀疑某个函数在某次发布后行为不同。
- **Atlas**：对钉住的两个版本各跑一次同一输入，给出两条 `observed` 记录；记录里写清超时、拒绝、未观测。
- **LLM**：根据观察差异提出假设和根因方向。
- **Atlas 的作用**：提供**可复现的观察**，而不是"我觉得应该是"。
- **今天**：受控执行能做，**跨版本对照的并排呈现没做**。

## 3. 代码不许出内网

- **人**：合规要求下 review 一个敏感模块。
- **Atlas**：本地索引、查询、关系与结构报告；全程不调用模型，令牌与内容都不出机器。
- **LLM**：不可用。这**不是缺陷，是产品**。
- **Atlas 的作用**：它是唯一选项。此时"没有 LLM"正是被购买的能力。
- **今天**：完全能做，而且这是 Atlas 最扎实的一条。

## 4. PR review：这个 diff 改了什么关系

- **人**：review 一个 800 行的 diff，只想看"关系变了什么"。
- **Atlas**：图差异——新增/删除了哪些调用边、哪些实体被改、受影响的测试与声明的 argv。
- **LLM**：解释改动意图、指出风险与遗漏。
- **Atlas 的作用**：把 review 从"读代码"变成"读关系变化"，且每条变化有锚点。
- **今天**：图差异与补丁链已实现；**没有把 diff 关系以 review 版式呈现**。

## 5. 新人建立心智地图

- **人**：入职第一周，要知道"这个项目由什么组成、我从哪进去"。
- **Atlas**：层级摘要、入口清单、每个模块的事实计数与聚合守恒；城市作为结构空间。
- **LLM**：讲"为什么这样分层"。
- **Atlas 的作用**：**呈现本身就是产品**——这一屏好不好看、读不读得懂，就是 Atlas 的成败。
- **今天**：层级与城市已实现；**概览仍是网格，密度与层次不够**。

## 6. 判断"这个函数能不能独立测"

- **人**：想给它加测试，不知道从哪下手。
- **Atlas**：可测试性画像（纯函数 / 需要上下文 / 需要入口驱动 / 不支持）、依赖包络、可声明的输入与必须承认的未知。
- **LLM**：写测试代码。
- **Atlas 的作用**：回答**"能不能测、怎么喂输入"**，不回答"测试内容"。
- **今天**：`profile` 有了；**页面里"生成候选测试"这个动作不存在**。

## 7. 重构前的爆炸半径

- **人**：想把一个工具函数改名/改签名。
- **Atlas**：全部已解析调用点 + **未解析部分显式列出** + 递归簇。
- **LLM**：机械改写、批量重命名。
- **Atlas 的作用**：**未解析的那部分必须出现在清单上**，否则重构一定会漏。这是 Atlas 与"grep 一下"的根本区别。
- **今天**：能查；**没有"爆炸半径"这个专门呈现**（把已解析与未解析放在同一张清单上）。

## 8. "这个函数有没有副作用"

- **人**：想知道它是不是纯的。
- **Atlas**：effects（可能调用谁、可能写堆、是否注册回调、是否逃逸局部值）+ 未知原因。
- **LLM**：不该被问这个问题——它会给出一个自信的猜测。
- **Atlas 的作用**：这是**只有 Atlas 能回答**的问题类型。
- **今天**：引擎能答；**页面上没有把 effects 做成一等结论**。

## 9. 讲架构给不写代码的人听

- **人**：技术负责人要向业务方解释系统结构。
- **Atlas**：结构规模、层级聚合、模块之间的调用候选（静态事实，不伪造运行）。
- **LLM**：写讲解词、打比方。
- **Atlas 的作用**：**呈现承担沟通**。数字必须能被引用，且经得起追问。
- **今天**：城市与层级已实现，尺度已修正；**没有讲解模式**（标注、书签、按顺序讲解）。

## 10. 反例：问"这段代码的业务逻辑是什么"

- **人**：想知道"为什么要这样写"。
- **Atlas**：**必须拒绝**——"这不在我的证据范围内"。这不是错误处理，是一等结论。
- **LLM**：该它上场，而且应该被告知"Atlas 没有这个事实，你要靠读代码和上下文"。
- **Atlas 的作用**：**明确的能力边界**。一个敢说"我不知道"的仪器，比一个什么都能答的仪器可信。
- **今天**：引擎层面一直这么做；**UI 把拒绝做成了红字提示，而不是一条正式结论**。

---

## 如果推翻 Atlas 重来，我会怎么定它

**「改代码之前的证据台」**：每一个输出都必须能回答"我现在能不能安全地做这个决定"；凡是回答不了这个问题的内容，都不该出现在首屏。

按这个标准，今天最该先做的三件事不是内核，而是：

1. **一屏四问的函数工作台**（场景 1/8）——让一个人能对"我要改的函数"做决定；
2. **爆炸半径清单**（场景 7）——把已解析和未解析放在同一张纸上；
3. **拒绝变成一等结论**（场景 10）——"我不知道"要有版式，不能是红字报错。

## 这份分工意味着什么（自我修正）

- 10 个场景里 **7 个的第一次接触点是屏幕**，所以"呈现优先"不是审美，是产品结构决定。
- 场景 3/8/10 说明：**Atlas 的拒绝能力是功能**，不是异常路径。
- 场景 6/7 说明：Atlas 该回答的是"**能不能 / 影响谁**"这类**封闭问题**，而不是试图替代"理解代码"。
- 我此前把力气花在机制完备上，本质是在回答一个没人问的问题。
